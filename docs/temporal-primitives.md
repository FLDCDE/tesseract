# Temporal Primitives

Core building blocks for working with time: **Moment** (a point in time) and **Interval** (a time span).

---

## TL;DR

**Moment** = A point in time (or infinity). Three types: finite timestamps (`14:30 UTC`), positive infinity (`∞`), and negative infinity (`-∞`).
Immutable, timezone-aware, blazingly fast comparisons thanks to singletons.

**Interval** = A time span `[start..end)` (half-open). Five types: bounded `[9:00..17:00)`, open-ended future `[now..∞)`, open-ended past
`(-∞..deadline)`, the entire timeline `(-∞..∞)`, and empty `∅`. Always immutable. Merge, intersect, query—all without mutating originals.

**Key insight:** Half-open intervals `[start..end)` mean adjacent slots `[9:00..12:00)` and `[12:00..17:00)` touch perfectly without gaps or overlaps.
No more "is the endpoint included?" debates. The Temporal Permit Office requires precision.

**Factory pattern:** `Moment` → `Moments`, `Interval` → `Intervals`. Add an 's'. Done.

## Foundation

> **Foundation:** All temporal data uses Java's `OffsetDateTime` for timezone-aware precision.  
> **Immutability:** Everything is immutable. Operations return new instances, never modify originals. Thread-safe by default.  
> **API Consistency Note:** You might notice that `intersect()` returns an iterator even though it only ever returns 0 or 1 intervals (and could use `Optional<Interval>` instead). This is intentional. Both `union()` and `intersect()` return iterators to maintain a consistent API—`union()` can return 1 or 2 intervals, and `intersect()` returns 0 or 1. Using the same return type for both means you can swap between them without rewriting your iteration logic. Sometimes API consistency trumps type precision.

## Moment

A point in time with support for infinity. Built on `OffsetDateTime` with cleaner comparison APIs.

> **Examples notation:** Throughout this document, we use helper methods like `moment(14)` and `interval(9, 17)` as shorthand. These create temporal objects relative to today's beginning in UTC. For example, `interval(9, 17)` means [9:00..17:00) UTC today. For complete implementation details, see [Helper Notation](helper-notation.md).

**Factory pattern:** In TesseractLib, primitives get their own factory classes in the core submodule. The naming convention? Add an 's'. Revolutionary, we know. `Moment` → `Moments`, `Interval` → `Intervals`, `Location` → `Locations`, `Presence` → `Presences`. Once you see the pattern, you'll never forget it (unlike that one time you spent 20 minutes looking for the `Interval` constructor).
**The Autocomplete Trap:** Beware: your IDE's code completion has learned this pattern *too* well. Type `geniusMethod(Collection<Interval>` and watch as it eagerly suggests `Intervals` with an 's'. This is *not* a factory call—you want the type `Interval`, not the factory class `Intervals`. When you see `Collection<Intervals>` in your code, that's autocomplete's revenge. 

**Implementation Types:**

TesseractLib provides three distinct moment implementations, each optimized for specific temporal scenarios:

1. **Finite Moment** — A specific point in time
   - Backed by `OffsetDateTime` with timezone information
   - Represents actual timestamps: "2025-11-03T14:30:00Z"
   - Example: Filing timestamp when form TPO-1471 was submitted (14:30 UTC)
   - Most common type for real-world temporal operations
   - Supports all comparison operations, time shifts, and timezone conversions
   - Implementation: `ImmutableFiniteMoment` (generated by Immutables library)

2. **Positive Infinite Moment** `∞` — The end of time (**singleton**)
   - Represents the furthest possible future
   - Always greater than any finite moment
   - Example: "Permit valid until... infinity" (when bureaucracy gives up on deadlines)
   - **Singleton**: Only one instance exists application-wide (`Moments.inf()`)
   - Used for: unbounded future intervals, "valid indefinitely" scenarios
   - Comparison optimization: `moment.isPositiveInfinite()` is faster than value comparison
   - Implementation: `ImmutablePositiveInfiniteMoment` (generated singleton by Immutables library)

3. **Negative Infinite Moment** `-∞` — The beginning of time (**singleton**)
   - Represents the distant past before time began
   - Always less than any finite moment
   - Example: "All filings since the dawn of bureaucracy" (which predates the universe)
   - **Singleton**: Only one instance exists application-wide (`Moments.ninf()`)
   - Used for: unbounded past intervals, "valid since forever" scenarios
   - Comparison optimization: `moment.isNegativeInfinite()` is faster than value comparison
   - Implementation: `ImmutableNegativeInfiniteMoment` (generated singleton by Immutables library)

> **Fun fact:** Singleton infinite moments use identity comparison (`==`) instead of value comparison—making them faster than explaining why they're fast. Ironically, checking if something represents "infinite time" takes essentially zero time. The Temporal Permit Office finds this philosophically satisfying.

### Creating Moments

```java
import com.fieldcode.tesseract.moment.Moments;
import java.time.OffsetDateTime;

// Finite moment (from OffsetDateTime)
var moment = Moments.moment(OffsetDateTime.now());

// Infinite boundaries
var positiveInfinity = Moments.inf();   // ∞
var negativeInfinity = Moments.ninf();  // -∞
```

**Why infinity?** For unbounded intervals like "available from 9 AM onwards" or "valid indefinitely." No more `null` checks or sentinel values.

### Moment Operations

**Comparisons:**

Temporal Compliance Officer Jenkins validates permit filing timestamps to ensure regulatory compliance:

```java
// Two permit filings arrive at different times
var citizenFilingTime = moment(9);      // Citizen filed at 9:00
var deadlineTime = moment(10);          // Deadline is 10:00

// Compare timestamps
citizenFilingTime.eq(deadlineTime);     // false - equals
citizenFilingTime.lt(deadlineTime);     // true - filed before deadline (earlier)
citizenFilingTime.gt(deadlineTime);     // false - not greater than (later)

// Additional comparisons available
citizenFilingTime.ne(deadlineTime);     // true - not equal
citizenFilingTime.le(deadlineTime);     // true - less than or equal
citizenFilingTime.ge(deadlineTime);     // false - not greater than or equal

// Result: Filing accepted (arrived before deadline)
```

**Comparable Support**

Moments are fully Comparable, so you can easily sort, find minimums and maximums, or perform any standard comparison operation. This makes it straightforward to determine the earliest or latest moment in any collection—no custom logic required.

For example, to find the earliest and latest meeting slots across timelines:

```java
var moments = List.of(moment(9), moment(14), moment(11));
var earliest = moments.stream().min(Comparator.naturalOrder()).orElseThrow();
var latest = moments.stream().max(Comparator.naturalOrder()).orElseThrow();
System.out.println("Earliest: " + earliest + ", Latest: " + latest);
// Output: Earliest: 2025-11-06T09:00Z, Latest: 2025-11-06T14:00Z
```

**Copy/Transform methods:**

Since moments are immutable, these methods create modified copies rather than changing the original:

```java
// Time shifting - Temporal Compliance Officer Jenkins processes permit amendments
// Original filing timestamp: 10:00 UTC
var originalFilingTime = moment(10);

// Amendment filed 2 hours later (citizen was stuck in paradox queue)
var amendmentTime = originalFilingTime.shift(Duration.ofHours(2));
// originalFilingTime unchanged at 10:00, amendmentTime is 12:00

// Retroactive filing permitted: go back 30 minutes (requires form TPO-8472)
var retroactiveTime = originalFilingTime.shift(Duration.ofMinutes(-30));
// Negative duration = backward time shift

// Timezone conversion - coordinating with Temporal Permit Office branches
// Main office timestamp in UTC
var mainOfficeTime = Moments.now();

// Convert to New York branch timezone (same instant, different representation)
var nyBranchTime = mainOfficeTime.withZoneIdSameMoment(ZoneId.of("America/New_York"));
// Useful for: "What time does the NYC branch see this filing?"

// Clamping - enforcing Temporal Operating Hours (9:00-12:00 only)
var citizenRequestTime = moment(14);  // 14:00 - after office hours!

// Clamp to valid office hours window [9:00..12:00]
var actualProcessingTime = citizenRequestTime.pull(moment(9), moment(12));
// Returns moment(12) - pulled to upper boundary of allowed range
// Result: "Your 14:00 request will be processed at 12:00 (latest available time)"
```

**String representation:**
```java
// Finite moment - returns ISO-8601 format from OffsetDateTime
var finite = Moments.moment(OffsetDateTime.parse("2025-11-02T14:30:00Z"));
System.out.println(finite.toString());  // "2025-11-02T14:30Z"

// Positive infinite - returns the infinity symbol
System.out.println(Moments.inf().toString());   // "∞"

// Negative infinite - returns negative infinity
System.out.println(Moments.ninf().toString());  // "-∞"
```


## Interval

A time span with a start and end. Always **half-open** `[start..end)`—includes start, excludes end.

> **Design choice:** All intervals are **half-open** `[start..end)`—the start moment is *included*, the end moment is *excluded*. This eliminates a whole class of bugs. Consider two adjacent time slots: `[9:00..12:00)` ends exactly when `[12:00..17:00)` begins. They touch but never overlap—no gap, no double-booking. You can split, merge, and query intervals without worrying about whether endpoints are inclusive or exclusive. The tradeoff? You can't represent fully-closed or fully-open intervals. We chose predictable behavior and performance over ultimate flexibility.

**Implementation Types:**

TesseractLib provides five distinct interval implementations, each optimized for specific temporal scenarios:

1. **BoundedInterval** `[start..end)` — Finite boundaries
   - Both start and end are finite moments
   - Has calculable duration
   - Example: Temporal permit valid from 9:00 to 17:00
   - Most common type for real-world scheduling
   - Implementation: `ImmutableBoundedInterval` (generated by Immutables library)

2. **IntervalFrom** `[start..∞)` — Open-ended future
   - Finite start, infinite end
   - No calculable duration
   - Example: "Permit valid from this moment forward until regulation changes"
   - Used for: ongoing obligations, indefinite validity periods
   - Implementation: `ImmutableIntervalFrom` (generated by Immutables library)

3. **IntervalTo** `(-∞..end)` — Open-ended past
   - Infinite start, finite end
   - No calculable duration
   - Example: "All historical filings up until this deadline"
   - Used for: retroactive compliance windows, historical data ranges
   - Implementation: `ImmutableIntervalTo` (generated by Immutables library)

4. **Always** `(-∞..∞)` — The entire timeline (**singleton**)
   - Both bounds are infinite
   - Covers all time that has ever existed or will exist
   - Example: The Filing Department's backlog (literally infinite paperwork)
   - **Singleton**: Only one instance exists application-wide (`Intervals.always()`)
   - Implementation: `ImmutableAlwaysInterval` (generated singleton by Immutables library)

5. **Empty** `∅` — No time at all (**singleton**)
   - Represents absence of time
   - Duration is zero, but has no actual temporal extent
   - Example: "Time available for processing form TPO-404: none"
   - **Singleton**: Only one instance exists application-wide
   - Used internally for representing "no intervals" in operations
   - Implementation: `ImmutableEmptyInterval` (generated singleton by Immutables library)

> **API Design Warning:** While the `Empty` interval type exists, **avoid using it directly in your APIs**. It can cause complications and make code harder to reason about. If your algorithm might return "no interval," prefer returning `Optional<Interval>` (for single results) or `Collection<Interval>` (for multiple results). The Empty type is primarily for internal use within the library's set operations. Returning `Optional.empty()` is clearer and more idiomatic than returning an Empty interval—it's the difference between "no result" (semantically correct) and "a result that represents nothing" (philosophically confusing, like filing a form to indicate you have no forms to file).

> **Performance note:** The singleton pattern for `Always` and `Empty` means identity checks (`==`) work for these special intervals, making comparisons extremely fast. The Filing Department's infinite backlog doesn't consume infinite memory—just one object reference.

### Creating Intervals

```java
import com.fieldcode.tesseract.interval.Intervals;

// Bounded interval - Temporal Permit Office operating hours
// Permits can only be filed between 9:00 and 17:00 (standard bureaucratic hours)
var officeHours = Intervals.interval(
    OffsetDateTime.now().withHour(9).withMinute(0),
    OffsetDateTime.now().withHour(17).withMinute(0)
);

// Unbounded intervals - because bureaucracy has no bounds

// Open-ended: "Valid from this moment forward, indefinitely"
// (until the next regulation change, form TPO-9001 required)
var validFromNow = Intervals.intervalFrom(start);   // [start..∞)

// Historical: "All time up until this deadline"
// (for retroactive compliance filings—yes, the deadline predates some events)
var validUntilDeadline = Intervals.intervalTo(end);     // (-∞..end)

// The Filing Department's backlog: spans all of time, literally
// (every moment that has ever existed or will exist needs paperwork)
var theEntireTimeline = Intervals.always();              // (-∞..∞)
```

### Basic Operations

```java
// Properties - inspecting a temporal permit's validity window
var permitWindow = interval(9, 17);
var permitStart = permitWindow.getLower();           // When permit becomes valid
var permitEnd = permitWindow.getUpper();             // When permit expires
var permitDuration = permitWindow.getDuration();     // How long it's valid (Optional<Duration>)
var isFinite = permitWindow.isBounded();             // Does it have an expiration? (not eternal)

// Relationships - checking temporal conflicts in schedule
var officeHours = interval(9, 17);         // Office open 9:00-17:00
var resolutionWindow = interval(14, 16);  // Resolution window 14:00-16:00

officeHours.intersects(resolutionWindow);    // true - they overlap (office open during resolution)
officeHours.contains(moment(10));             // true - 10:00 is within office hours
officeHours.encloses(resolutionWindow);      // true - resolution window entirely within office hours

// Algebra - combining temporal schedules (returns iterators or new intervals)
var morningShift = interval(6, 14);
var afternoonShift = interval(12, 20);

var overlap = morningShift.intersect(afternoonShift);    // FluentIterator<Interval>
// Result: [12:00..14:00) - when both shifts overlap (handoff period)

var fullCoverage = morningShift.union(afternoonShift);   // Iterator<Interval>
// Result: [6:00..20:00) - combined coverage (merged because they overlap)

var totalSpan = morningShift.span(afternoonShift);       // Single spanning Interval
// Result: [6:00..20:00) - from earliest start to latest end

// Transformation - temporal shift for processing delays
var filingDeadline = interval(9, 10);
var delayedDeadline = filingDeadline.shift(Duration.ofHours(2));  // New interval [11:00..12:00)
// "Due to temporal anomaly, deadline extended by 2 hours" (form TPO-5555 filed in triplicate)
```

### Allen's Interval Algebra

**Understanding temporal relationships:** When Administrator Chen analyzes two intervals, there are exactly 13 possible relationships between them (no more, no less—James Allen proved this mathematically in 1983). The `getRelationTo()` method returns an `IntervalsRelation` object that describes how interval A relates to interval B.

> [Allen's interval algebra](https://en.wikipedia.org/wiki/Allen%27s_interval_algebra) is a core model for reasoning about temporal intervals. It
defines 13 unique relationships that can exist between any two intervals, covering every possible arrangement of their start and end points. This
makes it especially useful for scheduling, temporal reasoning, and conflict detection—the exact kinds of challenges the Temporal Permit Office deals
with every day.

**The 13 Relations:**

```java
// Get the relationship between two intervals
var permit = interval(9, 17);           // Office permit: 9:00-17:00
var meeting = interval(14, 16);         // Scheduled meeting: 14:00-16:00

var relation = permit.getRelationTo(meeting);

// Check specific relationship types
relation.contains();      // true - permit contains the meeting
relation.during();        // false - permit is not during meeting
relation.overlaps();      // false - permit doesn't just overlap, it fully contains
```

**Common Temporal Relations:**

```java
// 1. BEFORE - A happens entirely before B (no touching)
var morningPermit = interval(9, 12);
var afternoonPermit = interval(14, 17);
morningPermit.getRelationTo(afternoonPermit).isBefore();  // true
// Morning: |-------|
// Afternoon:           |-------|

// 2. MEETS - A's end exactly touches B's start
var shift1 = interval(9, 17);
var shift2 = interval(17, 22);  // Starts exactly when shift1 ends
shift1.getRelationTo(shift2).meets();  // true
// Shift1: |--------|
// Shift2:          |-------|

// 3. OVERLAPS - A starts before B, ends during B
var morning = interval(8, 12);
var midday = interval(10, 14);
morning.getRelationTo(midday).overlaps();  // true
// Morning: |----------|
// Midday:        |----------|

// 4. STARTS - A and B start together, A ends first
var briefing = interval(9, 10);
var fullMeeting = interval(9, 12);
briefing.getRelationTo(fullMeeting).starts();  // true
// Briefing:    |--|
// Full meeting:|-------|

// 5. DURING - A is completely inside B
var lunchBreak = interval(12, 13);
var workday = interval(9, 17);
lunchBreak.getRelationTo(workday).during();  // true
// Lunch:       |--|
// Workday: |----------|

// 6. FINISHES - A and B end together, A starts later
var finalHour = interval(16, 17);
var fullShift = interval(9, 17);
finalHour.getRelationTo(fullShift).finishes();  // true
// Final hour:      |--|
// Full shift: |-------|

// 7. EQUALS - A and B are identical
var permit1 = interval(9, 17);
var permit2 = interval(9, 17);
permit1.getRelationTo(permit2).equalsTo();  // true
// Both:    |-------|
```

**Inverse Relations:**

The remaining 6 relations are inverses of the above:

```java
// 8. IS_FINISHED_BY - inverse of FINISHES
fullShift.getRelationTo(finalHour).isFinishedBy();  // true

// 9. CONTAINS - inverse of DURING
workday.getRelationTo(lunchBreak).contains();  // true

// 10. IS_STARTED_BY - inverse of STARTS
fullMeeting.getRelationTo(briefing).isStartedBy();  // true

// 11. IS_OVERLAPPED_BY - inverse of OVERLAPS
midday.getRelationTo(morning).isOverlappedBy();  // true

// 12. IS_MET_BY - inverse of MEETS
shift2.getRelationTo(shift1).isMetBy();  // true

// 13. IS_AFTER - inverse of BEFORE
afternoonPermit.getRelationTo(morningPermit).isAfter();  // true
```

**Practical Example - Permit Conflict Detection:**

```java
// Temporal Compliance Officer Jenkins checks for permit conflicts
public boolean hasConflict(Interval existingPermit, Interval newRequest) {
    var relation = existingPermit.getRelationTo(newRequest);
    
    // Conflicts occur when intervals overlap in any way
    // Non-conflicting relations: before, meets, isAfter, isMetBy
    // Note: EQUALS also counts as a conflict (same time slot cannot be double-booked)
    return !(relation.isBefore() || 
             relation.meets() || 
             relation.isAfter() || 
             relation.isMetBy());
}

// Test cases
var permit = interval(9, 17);

hasConflict(permit, interval(18, 20));  // false - new permit is after
hasConflict(permit, interval(17, 20));  // false - new permit meets (touches)
hasConflict(permit, interval(14, 16));  // true - new permit during existing
hasConflict(permit, interval(8, 10));   // true - new permit overlaps
hasConflict(permit, interval(16, 19));  // true - overlapped by new permit

// Result: Jenkins can automatically flag conflicting permit requests
```

**Why This Matters:**

Allen's Interval Algebra provides a complete vocabulary for describing temporal relationships. When the Temporal Permit Office needs to determine if two permits conflict, or if a meeting fits within office hours, or if a resolution window overlaps with citizen appointments—these 13 relations express every possible scenario. No edge cases, no ambiguity. Just precise temporal reasoning.

> **Mathematical completeness:** These 13 relations are exhaustive and mutually exclusive. Given any two intervals, exactly one relation holds. This makes temporal logic deterministic and predictable—critical when managing time-travel permits where precision prevents paradoxes.

> **Convenience shortcuts:** While the examples above show the pure Allen's Temporal Algebra way (checking specific relations like `isBefore()`, `contains()`, etc.), the `IntervalsRelation` interface provides convenient shortcut methods for common use cases. For example, instead of checking `!(relation.isBefore() || relation.meets() || relation.isAfter() || relation.isMetBy())` to detect conflicts, you can use `relation.distinct()` which returns `true` when intervals don't overlap. Other shortcuts include methods that combine multiple Allen relations into single, readable checks. Use the explicit relation checks when you need precise temporal semantics; use the shortcuts when you need concise, readable code for common patterns.

### Quick Example

```java
var morning = interval(8, 12);
var meeting = interval(10, 11);

morning.intersects(meeting);           // true
morning.encloses(meeting);             // true
morning.intersects(interval(12, 13));  // false (touching, not overlapping)

var overlap = morning.intersect(meeting)
    .findFirst()
    .orElse(null);  // [10:00..11:00)
```



## DirectedInterval

A directed interval combines an `Interval` with a `QueryDirection` (FORWARD or BACKWARD). This is primarily used when querying collections where the direction of traversal matters—like reading timeline events forward chronologically or backward in reverse.

The directed interval was invented to simplify the query methods in the TesseractLib library. Instead of having two parameters like `query(interval, direction)`, a single `query(directedInterval)` parameter packages the interval and direction together.

### Creating DirectedIntervals

```java
// Create an interval for office hours
var officeHours = interval(9, 17);  // 9:00 to 17:00

// Method 1: Instance methods (easier, recommended)
var forwardQuery = officeHours.forward();
// Chronological order (oldest to newest) - use for processing permits in submission order

var backwardQuery = officeHours.backward();
// Reverse chronological (newest to oldest) - use for finding the most recent permit first

// Method 2: Factory method (when direction is dynamic)
var directedQuery = officeHours.directed(QueryDirection.FORWARD);
// Or: Intervals.directed(officeHours, QueryDirection.FORWARD)

// Access components
var window = forwardQuery.getInterval();        // The time window being queried
var direction = forwardQuery.getDirection();    // FORWARD or BACKWARD
```
